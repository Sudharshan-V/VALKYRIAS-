Scope: React application, Spring Boot controllers/services/repositories/entities, `setup_schema.sql`, and `database/migrations/**`.

## Existing-table decision

- Reuse `public.users`, `client_profiles`, `editor_profiles`, and normalized editor profile collections unchanged.
- Reuse `portfolio_items` only after associating it with the local editor/application user in authorized APIs; do not treat its old per-Auth-user rows as trusted published work.
- The flat `projects`, `chat_messages`, `deliverables`, and `action_items` records do not contain enough relational information to infer order ownership, assignment, participation, sender identity, payment gates, or file authorization. Existing rows must be preserved, but automatically converting them would attach ambiguous demo data to real accounts. The production domain therefore uses normalized additive tables and leaves legacy rows untouched for an explicit reviewed migration.
- `plans` is user-owned in the old schema, while services/packages are globally managed published catalog data. It cannot safely become the authoritative catalog without deciding which user's rows win. Existing rows remain intact; new catalog tables are authoritative.
- `notes` and `app_settings` remain legacy-compatible but are not authoritative for orders, verified finance, or Storage usage.

## Retained non-business presentation behavior

- Neumorphic layout, colors, spacing, typography, animations, loading visuals, and toast-dismiss timers.
- Generic form placeholders and marketing copy that do not claim to be persisted records.
- `setTimeout(..., 0)` used to defer authentication work outside the Supabase auth callback lock; it is not a simulated request.
- Stock/placeholder imagery only where it is explicitly a visual fallback, never as a persisted portfolio, file, project, or user record.

## Replacement result

The production context now initializes business collections empty and hydrates them through role-scoped dashboard/domain APIs. Orders, requirements, assignment, chat, files, notifications, workflow events, payment state, services/packages, and dashboard aggregates use persisted backend responses. Logout and account switching stop Realtime, clear account-specific state, and refetch after the next verified session. The remaining timers are UI dismissal/debounce/auth-callback scheduling, and remaining randomness is success-confetti layout; neither creates a business record.

The payment provider is deliberately an incomplete external boundary: no fake completion and no card/UPI/bank credential collection remain. A pending payment record is created through Spring and only a trusted server operation can mark it paid. See `docs/dynamic-application-architecture.md` for the provider and live-validation steps.
